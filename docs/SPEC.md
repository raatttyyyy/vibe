# Vibe: техническое задание

Vibe — рабочее название языка программирования, на котором описывают разработку программного продукта силами ИИ-агентов: самих агентов, их задачи, контекст, модели и проверки результата. Одновременно это учебный язык: он обязан пройти шесть этапов курса и содержать классические конструкции.

Этот документ фиксирует, что должно быть сделано. Зачем и для кого — в [PRD.md](PRD.md), в каком порядке — в [DEV_PLAN.md](DEV_PLAN.md), как модули стыкуются в коде — в [API.md](API.md).

**Статус:** версия 0.1 от 10.11.2026. Разделы про генерацию и исполнение намеренно краткие: они будут дополняться в `docs/generation/` и `docs/execution/`.

## 1. Источники требований

1. **Установки курса** — записи с доски и конспект (фото от 10.11.2026). Обязательны: этапы принимает преподаватель.
2. **Решения команды** — ответы на уточняющие вопросы 09–10.11.2026.
3. **Предложения из обсуждения** — действуют, пока не противоречат пунктам 1 и 2.

При противоречии действует источник с меньшим номером.

Требования пронумерованы, чтобы на них можно было ссылаться: `К` — обязательная часть языка по курсу, `А` — агентная часть, `G`, `LEX`, `SYN`, `SEM`, `GEN`, `RUN` — требования к модулям, `N` — общие.

## 3. Требования к языку

### 3.1. Общие решения

- **L-1.** Синтаксис C-подобный: блоки в фигурных скобках, операторы завершаются `;`. Пробелы, табуляции и переводы строк значения не имеют.
- **L-2.** Типизация статическая, с явным указанием типов.
- **L-3.** Язык общего назначения: на нём можно написать обычную программу без единого агента.
- **L-4.** Исходные файлы — текст в UTF-8 с расширением `.vibe`. Идентификаторы состоят из латинских букв, цифр и `_`; в строках и комментариях допустим любой текст.
- **L-5.** Программы бывают двух видов: с точкой входа `func void main()` (отработала и завершилась) и с обработчиками событий `on` (работают внутри долгоживущего оркестратора).
- **L-6.** Программы пишут и человек, и ИИ. Поэтому у каждой конструкции один способ записи, а сообщения об ошибках точные.

### 3.2. Обязательная часть (требования курса)

| № | Требование с доски | Что это значит в Vibe |
|---|---|---|
| К-1 | Типы `int`, `double`, `bool`, `char` | Четыре встроенных простых типа |
| К-2 | Строки и динамические контейнеры | Тип `string`; как минимум динамический массив с индексацией. Квадратные скобки в исходнике используются только как суффикс индексации. Состав контейнеров фиксирует грамматика |
| К-3 | Операции: арифметика, логика, сравнения, вызов, индексация, запятая | `+ - * / %`, унарный минус; `&& \|\| !`; `== != < <= > >=`; `f(a, b)`; `a[i]`; операция `,` |
| К-4 | `=` — операция либо оператор | Выбрано: операция. Присваивание — правоассоциативное выражение со значением: `a = b = c` |
| К-5 | Ветвление | `if` и `else` |
| К-6 | Циклы `for`, `while`, `do while`; `break`, `continue`, `goto` | Все перечисленные. `goto` ограничен (см. SEM-6) |
| К-7 | Функции | Определение начинается с `func`. Поддерживаются параметры, возвращаемое значение, `void` и рекурсия |
| К-8 | Ввод и вывод | Чтение значений простых типов и строк из стандартного ввода, запись в стандартный вывод. Форму записи фиксирует грамматика |
| К-9* | Любые свои возможности | Агентная часть, раздел 3.3 |

Дополнительно к списку с доски:

- **Перечисления** `enum` — есть в образце грамматики с доски (`<DefEnum>`).
- **Классов нет** (решение команды): ни методов, ни наследования.
- **Структуры** `struct` — записи из полей без методов. Оставлены, потому что без них не описать тип ответа агента (А-2). Это допущение, см. раздел 7.

### 3.3. Агентная часть

Входит в первую версию:

- **А-1. Модели и агенты.** Модель объявляется с параметрами. Агент — неизменяемое описание: модель, запасные модели на случай провала, инструменты, бюджет, способ изоляции.
- **А-2. Типизированный ответ.** Результат обращения к агенту — значение объявленного типа. Транслятор строит схему из типа, среда исполнения проверяет по ней ответ модели. Несоответствие — ошибка, а не строка «как получилось».
- **А-3. Промпт-литерал.** Отдельный вид литерала для текста запроса с подстановкой выражений.
- **А-4. Контекст как область видимости.** Блок `context` задаёт, что видит агент. `use` добавляет источник, `hide` скрывает его для вложенных вызовов. Агент видит ровно то, что подключено в объемлющих блоках.
- **А-5. Проверка результата.** Блок `attempt (N)` повторяет тело, пока не выполнятся все `ensure`. Причина проваленной проверки попадает в следующую попытку. Судья — обычный агент, чей типизированный вердикт проверяется через `ensure`. После N неудач — ошибка.
- **А-6. Задачи и параллелизм.** `task` объявляет задачу, `spawn` запускает её и возвращает `future<T>`, `await` ждёт результат. Из этих зависимостей получается граф параллельного исполнения.
- **А-7. Бюджеты и права.** У агента объявлены бюджет (деньги, токены, время) и права (файлы, команды, сеть). Что можно, проверяется при трансляции (SEM-8); остальное — при исполнении.
- **А-8. Изоляция.** Агент работает в собственном рабочем каталоге git (worktree).
- **А-9. Обработчики событий.** `on событие(...) { ... }` регистрирует реакцию в долгоживущем оркестраторе.

Отложено на следующие версии:

- общая память агентов (`board`);
- сохранение графа в базе данных и возобновление после остановки;
- участие человека во время исполнения: вопросы, подтверждения, вмешательство;
- клиент MCP;
- запуск готовых агентов (Cursor, Claude Code и подобных) вместо собственного цикла.

### 3.4. Как это выглядит

Пример показывает замысел. Точный синтаксис задаёт грамматика в `docs/grammar/`, и он может отличаться.

```
struct Verdict { bool ok; string reason; }

model fast   { id: "small-model"; }
model strong { id: "large-model"; }

agent Fixer {
    model:  fast else strong;
    tools:  (fs.read("**"), fs.write("src/**"), sh.run("npm test"));
    budget: 2usd, 20min;
    space:  worktree;
}

agent Judge {
    model: strong;
    tools: (fs.read("**"));
}

task Patch fix(CiRun run) {
    context {
        use fs.file("AGENTS.md");
        use run.log.tail(200);

        attempt (3) {
            Patch p = Fixer.ask(`CI упал на шаге ${run.step}. Найди причину и исправь.`);
            ensure sh.run("npm test").ok : "тесты не проходят";
            Verdict v = Judge.ask(`Оцени патч: ${p.diff}`);
            ensure v.ok : v.reason;
            return p;
        }
    }
}

on ci.failed(CiRun run) {
    future<Patch> f = spawn fix(run);
    Patch p = await f;
    gh.open_pr(p);
}
```

## 4. Требования к модулям

### 4.1. Грамматика

- **G-1.** Нотация курса — форма Бэкуса–Наура: нетерминалы в угловых скобках, `::=`, `|`, необязательная часть в `[ ]`, повторение ноль и более раз в `{ }`.
- **G-2.** Грамматика покрывает весь язык: К-1…К-8 и А-1…А-9. Отдельно описана лексика: какие бывают лексемы и как они записываются.
- **G-3.** Верхний уровень строится по образцу с доски:

  ```
  <Program>    ::= <Definition><Program> | <Declaration><Program> | EOF
  <Definition> ::= <DefFunc> | <DefClass> | <DefEnum>
  <DefFunc>    ::= "func" <Typevoid> <id> ( [ <param_list> ] ) <block>
  <Typevoid>   ::= <Type> | void
  ```

  `<DefClass>` заменяется определением структуры; добавляются определения модели, агента, задачи и обработчика.
- **G-4.** Грамматика пригодна для рекурсивного спуска: без левой рекурсии, выбор правила делается по текущей лексеме. Места, где одной лексемы мало, перечислены явно.
- **G-5.** Приоритет и ассоциативность операций заданы уровнями правил, как в конспекте:

  ```
  <E> ::= <T> { + <T> }
  <T> ::= <F> { * <F> }
  <F> ::= <Num> | ( <E> )
  <A> ::= <I> | <I> = <A>
  ```

  К грамматике прилагается таблица приоритетов. Присваивание правоассоциативно, запятая имеет низший приоритет.
- **G-6.** Грамматика однозначна. Если телом `if` может быть одиночный оператор, записано правило: `else` относится к ближайшему `if`.
- **G-7.** К грамматике прилагаются примеры: правильные программы на каждую конструкцию и неправильные с указанием, какое правило нарушено.

Набросок грамматики из обсуждения 10.11.2026 этим требованиям не соответствует и служит только источником идей для агентных конструкций. В нём другая нотация, нет `char`, `double`, `do while`, `goto`, цикла `for` в стиле C, операции «запятая» и ввода-вывода, а присваивание сделано оператором.

### 4.2. Лексический анализ

- **LEX-1.** Вход — текст программы. Выход — последовательность лексем, которая заканчивается служебной лексемой конца файла.
- **LEX-2.** Анализ идёт за линейное время, одним проходом, на конечном автомате, написанном вручную.
- **LEX-3.** Ключевые слова, в том числе `func`, распознаются бором.
- **LEX-4.** Типы лексем — как на доске: `keyword`, `operator`, `literal`, `id`, `delimiter`, `unknown`. К ним добавлен служебный тип конца файла.
- **LEX-5.** У каждой лексемы есть тип, исходный текст и позиция: строка и столбец.
- **LEX-6.** Выбирается самая длинная подходящая лексема: `a+++b` разбирается как `a`, `++`, `+`, `b`.
- **LEX-7.** Лексер не проверяет синтаксис: `a = if : b` — допустимая последовательность лексем.
- **LEX-8.** Лексические ошибки: недопустимый символ (`#` в `if (a > #b)`), неверно записанное число (`3.5.7`), незакрытые строка, символ или комментарий. Ошибочный фрагмент становится лексемой `unknown`, выдаётся сообщение, анализ продолжается до конца файла.
- **LEX-9.** Пробельные символы и комментарии пропускаются и лексемами не являются. На доске пример с лексемами `\n` и `\t` относится к синтаксису с отступами; в Vibe он не применяется (L-1).
- **LEX-10.** Если грамматика вводит промпт-литерал с подстановками (А-3), лексер делит его на текстовые части и вложенные выражения.

### 4.3. Синтаксический анализ

- **SYN-1.** Вход — последовательность лексем. Выход — дерево разбора программы.
- **SYN-2.** Метод — рекурсивный спуск, написанный вручную: одна функция на нетерминал, текущая лексема и переход к следующей (в конспекте `t` и `gt()`).
- **SYN-3.** Дерево строится, как в конспекте:
  - левоассоциативные операции — циклом, новый узел становится левым поддеревом следующего: `5 + 3 + 7` даёт `(5 + 3) + 7`;
  - присваивание — рекурсией, правоассоциативно;
  - у узла `if` три потомка: условие, ветка «то», ветка «иначе»; если `else` нет, третий потомок пуст.
- **SYN-4.** После разбора начального нетерминала проверяется, что текущая лексема — конец файла.
- **SYN-5.** Синтаксическая ошибка сообщает позицию, что ожидалось и что встретилось. В первой версии разбор останавливается на первой ошибке, как в конспекте; продолжение после ошибки — позже.
- **SYN-6.** Парсер не проверяет имена и типы.
- **SYN-7.** Если лексер сообщил об ошибках, синтаксический анализ не запускается.
- **SYN-8.** Дерево можно вывести текстом — для сдачи этапа и для тестов.

### 4.4. Семантический анализ

- **SEM-1. Имена.** Имя объявлено до использования. Повторное объявление в той же области видимости — ошибка.
- **SEM-2. Типы.** У каждого выражения есть статический тип; операции, индексация и обращения к полям проверяются. Неявное преобразование одно: `int` в `double`.
- **SEM-3. Присваивание.** Слева стоит то, чему можно присвоить: переменная, элемент по индексу, поле. Тип выражения присваивания — тип левой части.
- **SEM-4. Функции.** При вызове проверяются число и типы аргументов. Функция с типом результата, отличным от `void`, возвращает значение на всех путях.
- **SEM-5. Условия.** Условие в `if`, `while`, `do while`, `for` имеет тип `bool`.
- **SEM-6. Переходы.** `break` и `continue` допустимы только внутри цикла. Для `goto`:
  - метка объявлена в той же функции и уникальна в ней;
  - переход возможен в свой блок или в объемлющий, но не внутрь другого блока, включая `context` и `attempt`;
  - переход вперёд не перепрыгивает объявление переменной в том же блоке.
- **SEM-7. Агентные конструкции.**
  - тип ответа агента представим схемой (А-2);
  - `use` и `hide` стоят внутри `context`;
  - `spawn` применён к вызову задачи, каждый `future` дождались;
  - свойства агента не повторяются.
- **SEM-8. Бюджеты и права.**
  - задача не требует от агента инструмент, которого у него нет;
  - вложенный агент не получает прав больше, чем у вызывающего;
  - сумма бюджетов вложенных вызовов не превышает бюджет объемлющего, когда это известно при трансляции.
- **SEM-9. Ошибки.** Сообщение содержит позицию. Анализ по возможности продолжается после ошибки, чтобы показать несколько ошибок за один запуск.
- **SEM-10. Результат** — дерево, в котором у выражений проставлены типы, а у имён — ссылки на объявления, плюс таблицы имён.

### 4.5. Генерация

- **GEN-1.** Вход — проверенное дерево и таблицы имён. Выход — исходный текст на C++20.
- **GEN-2.** Трансляция простая: классические конструкции переводятся в соответствующие конструкции C++, агентные — в вызовы библиотеки времени исполнения.
- **GEN-3.** Программа, прошедшая семантический анализ, даёт C++-код, который собирается. Ошибка компилятора C++ в сгенерированном коде считается ошибкой транслятора.

### 4.6. Исполнение

- **RUN-1.** Библиотека времени исполнения на C++ реализует А-1…А-9.
- **RUN-2.** Агентов исполняет собственный цикл, который обращается к моделям напрямую через их API. Ключи берутся только из переменных среды.
- **RUN-3.** Любое действие с побочным эффектом (вызов модели, команда, запись файла) проходит через одну точку, где проверяются права и списывается бюджет.
- **RUN-4.** В первой версии состояние между запусками не сохраняется: после остановки оркестратора незавершённые задачи теряются.

## 5. Общие требования

- **N-1.** Язык реализации — C++20, сборка — CMake, тесты — GoogleTest.
- **N-2.** Транслятор собирается и работает на Windows, Linux и macOS.
- **N-3.** Лексер и парсер пишутся вручную: генераторы анализаторов и библиотеки регулярных выражений не используются.
- **N-4.** Этапы не смешиваются: каждый модуль делает свою работу и передаёт результат дальше через интерфейсы из [API.md](API.md).
- **N-5.** Следующий этап не запускается, если предыдущий сообщил об ошибках.
- **N-6.** Формат сообщения об ошибке единый для всех этапов: файл, строка, столбец, код ошибки, текст.
- **N-7.** На каждое требование этапов 2–4 есть тест, включая примеры с доски.
- **N-8.** Чтобы запустить программу на Vibe, пользователю нужен компилятор C++20 — следствие GEN-1.
